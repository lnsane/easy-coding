# easyCode v0.6.0

> 润色改为纯 stdin 管道：内容由应用读回后经管道送入 Claude Code，不再依赖 `Read` 工具自己读文件。
> 日期：2026-09-27

## 变更背景

v0.4.1 起润色用的是「文件模式」——把文档路径告诉 Claude Code，让它用 `Read` 工具自己去读：

```
claude -p --tools Read --append-system-prompt <规则>
```

用户提出两个问题：

1. 这种「给 Read 工具让它自己读」的方式不理想，希望能用**管道**把内容送进去
2. 希望沿用 Windows + Claude Code CLI 的方案

## 本版本变更

### 润色改为纯管道

两种模式**都不授予任何工具**（`--tools ""`）：

| | v0.4.1～v0.5.0 | v0.6.0 |
| --- | --- | --- |
| 命令 | `--tools Read`（让它自己读） | **`--tools ""`**（全禁） |
| 内容来源 | 它用 Read 读 `doc/xxx.md` | **应用读回文件内容 → stdin 管道送入** |
| 工作目录 | 项目根 | 项目根（不变） |
| shell | `false` | `false`（不变） |

具体流程：

1. 应用先从 `<项目>/doc/xxx.md` 读回磁盘上的最新内容（该文件由自动保存同步写入）
2. 内容经 **stdin 管道** 写给子进程
3. 工作目录仍是项目根，因此 `CLAUDE.md` 等上下文依然生效——**这靠的是 cwd，不是 Read 工具**

若文件不存在或内容为空，会记一条日志并**回退到编辑器里的内容**，不会静默失败。执行日志现在会显示内容取自哪里：

```
信息  管道模式：内容取自 doc/markdwon的润色测试.md（1418 字符）
命令  claude -p --tools "" --append-system-prompt <润色规则>   # 内容经 stdin 管道传入，1418 字符
```

### 为什么坚持 `shell: false` + stdin

- 避开 shell 解释：文档里的 `$` `%` `` ` `` `"` `|` `^` `&` `<` `>` 与反斜杠都不会被当成命令语法
- 绕开 Windows 约 32KB 的命令行长度上限（实测 336KB 文档可正常送达）

## 验证

新增 L12（`test-polish-pipe.mjs`，15 项），并**重写 L11**。

### L12：管道可靠性

- **shell 特殊字符不被破坏**：`$100`、`50%`、`` `code` ``、`C:\Users\test`、`"hi"`、`|`、`^`、`&`、`<tag>` 全部原样保留——这正是 `shell: false` 的价值
- **工具全禁**：放哨兵文件要求它读取并删除 → 内容没泄露、文件还在
- **长文档**：336KB 文档经管道成功送达（远超命令行上限）

### L11：重写为「只读保证」

原 `test-polish-filemode.mjs` 验证的是 `--tools Read` 这种已废弃的调用方式。留着它会误导后来者以为应用仍这么调。改为验证两条**与实现方式无关**的保证：

1. 无论怎么调，**磁盘文件都不能被改动**（哈希比对）
2. 项目 `CLAUDE.md` 的术语约定仍生效（**靠 cwd，不靠 Read 工具**）

**十二层合计 332 项断言全部通过。**

## 测试自身踩的两个坑

这两次失败**都不是代码问题，而是测试写错了**：

**1. 反斜杠被 JS 转义吃掉。** 写 `'C:\Users\test'` 做测试输入，但 `\U` 与 `\t` 都是**合法 JS 转义**，导致**输入本身**就少了一个反斜杠——测试失败，问题却在测试。改用 `String.fromCharCode(92)` 拼接才准。

**2. 长文档测试超时但偶发。** 首次通过、二次失败。不是代码问题，是 200s 超时对 336KB 文档偏紧，加到 400s 后稳定。

这两条与 v0.5.0 记录过的 `/\bBash\b/` 误判是同一类问题：**测试自身不可靠，比测不出 bug 更危险**——一个偶发失败的测试会让人习惯性重跑，从而错过真实回归。

## 已知事项

- 管道模式下不再需要 `Read` 工具，因此**没有任何工具权限**，比文件模式更收敛
- 关联项目时仍会把 cwd 设为项目根，`CLAUDE.md` 上下文照常生效
- 未关联项目时走同一套管道，只是内容取自编辑器正文
- 「执行编排任务」功能不受本次改动影响（它仍按设计使用读写工具）
