# easyCode v0.8.0

> 新增「生成开发计划文档」功能；顺带修掉一个影响**已有功能**的缺陷——CLI 噪音行被写进文档。
> 日期：2026-09-27

## 1. 新功能：生成开发计划文档

编辑器顶栏「✨ 润色」旁新增 **「📋 生成开发计划」** 按钮。

点开后在弹窗里确认文件名（默认「开发计划-&lt;需求标题&gt;」，可改；重名自动加序号），确认后：

1. 依据当前需求文档内容，让 Claude Code 产出一份计划
2. 计划写入项目 `doc/` 下，并**登记为一条新创作**，可直接打开继续编辑

### 产出结构

`需求理解` → `任务拆解` → `技术方案` → `风险与依赖` → `验收标准`

要求模型：任务拆到可独立完成与验证的粒度；需求没写清的地方放进「风险与依赖」作为待确认事项，**不替用户拍板**；不发明需求里没有的功能。

### 与润色的模式区别

| | 润色（关联项目） | 生成开发计划 |
| --- | --- | --- |
| 工具 | `Read,Write,Edit` + `--dangerously-skip-permissions` | **`Read,Glob,Grep`（只读检索）** |
| 能否改磁盘 | 能改指定文档 | **不能**（实测建不了文件、哨兵哈希不变） |
| 产出方式 | 直接写回文件 | 打印到 stdout，**由应用落盘** |

计划功能用只读检索，是刻意的：

- **需要读**：否则它只能照需求文本推演。实测第一版（`--tools ""`）把「角色配置 / 持久化 / 界面」列成待做任务——而那些**已经实现**了，因为需求文档写于开发之前。
- **不能写**：计划只需产出文本，落盘由应用统一掌控（文件名、路径、重名处理都在应用侧）。
- 只读工具**不需要** `--dangerously-skip-permissions`（实测 `Read/Glob/Grep` 无该参数即可用；写了才需要）。

改用只读检索后，同一份需求文档的产出一变为：

> 「这份需求的验收标准三条，当前代码**基本已实现**，剩余的是三个具体缺陷和一个『设计好但没接线』的功能。」

并带具体行号引用（`types.ts:108-130` 的 `Role`、`db.ts:98-107` 的 roles 表、`DocEditor.tsx:594-614` 的执行按钮）。产出结构也相应加了「现状盘点」一节，并要求**已实现的不列入任务拆解**。

### 它发现的一个真实缺陷（已修）

模型在「现状盘点」里指出：`Creation.roleId` 列、迁移代码、`db.setCreationRole()`、IPC `role:set-for-creation`、preload 声明**全都存在，但渲染层从未调用**——一条完整的死链路。同时 `createCreation()` 的 INSERT **不含 `role_id`**。

我核实了，**两条都属实**：

- `setCreationRole` 只有 preload 声明与 main handler，渲染层无任何调用
- `createCreation` 的 INSERT 列里确实没有 `role_id`，所以 `creation.roleId` 永远为 null、执行弹窗的默认角色永远为空

影响：功能上无害（用户仍可在弹窗里临时选角色），但代码里留着一条半截链路，且 `DocEditor` 在读一个永远为 null 的值。

**已修**：`createCreation` 写入 `role_id`；store 增加 `setCreationRole` action；执行时把选用的角色记为文档默认值。`CreationInput` 补 `roleId` 字段。

### 又修了两个「执行编排任务」的缺陷

修复第一条后重新生成计划，产出里又指出「执行编排任务」链路存在两个问题。核实**都属实**：

**1. 落库的执行日志恒为空/错位。**
`DocEditor.tsx` 里 `saveRun` 传的是 `log: runLogs`，而 `startOrchestrate` 是 `useCallback`——闭包里的 `runLogs` 是「回调创建那一刻」的旧数组。执行期间 `setRunLogs` 累积的新日志**永远进不去**，所以存进 `runs` 表的 log 要么空、要么是上一次的。

修法：加 `orchLogsRef`，在日志回调里同时写 state 与 ref；落库时读 ref。开跑前一并清空，避免串到上一轮。

**2. 用户主动「中止」被当成失败弹错。**
`orchestrate()` 在中止时返回 `ok:false`，而 `if (!r.ok) setOrchestrateError(...)` 在 cancelled 判断**之前**执行，于是用户点了中止会看到红色错误横幅，像是出错了。

修法：先判 `meta.status === 'cancelled'`，再判失败。

> 这两个缺陷是「生成开发计划」的只读检索能力带来的额外收获：它读了 `DocEditor.tsx` 的实际代码，指出闭包捕获与判断顺序的问题。说明给计划功能开只读检索不只是「避免把已实现的当待做」，还能起到代码审查的作用。

## 2. 修掉一个影响已有功能的缺陷

**现象**：`claude` CLI 会在 **stdout** 打印一行诊断信息：

```
[claude-code:unrecognized_model] {"model":"cline-pass/deepseek-v4.1-flash","query_source":"generate_session_title"}
```

这不是模型产出，但**混在 stdout 里**。此前 `polish.ts` 与 `plan.ts` 都没过滤它，于是：

- 润色时它会被当成文档的**第一行**（写进文件）
- 生成计划时它出现在标题之前，导致「产出不是有效 markdown」

**修法**：新增 `src/main/cli-output.ts`，提供 `cleanCliOutput()`，统一做两步清理——剥掉整篇代码围栏 + 去掉首尾的 `[claude-code:...]` 噪音行与空行。**只清首尾**，不动正文中间的内容（正文里若真有类似文字，那是用户内容，不该被改）。润色与计划两条链路都用它。

> 说明：这个缺陷不是我这次引入的，而是**一直存在**——上一版把 CLI 输出当作正文时就已经如此。是这次为计划功能写测试时才暴露出来。

## 3. 测试与两次「测试自身不可靠」

新增 L15（`test-plan-generate.mjs`，16 项）：结构完整性、可直接落盘、不编造需求、只读不改磁盘。

**十三层合计 357 项断言全部通过。**

过程中踩到两个问题，**都不是产品代码的错，而是测试写法不对**，但值得记下来：

### 3.1 测试自抄了一份 prompt，与实现漂移

测试脚本里另抄了一份 system prompt。我改了 `plan.ts` 里的提示词（加入「你没有可用工具，不要尝试调用」），测试却仍用旧措辞——于是出现「**修好了实现，测试却依然失败**」。

修法：把 prompt 提取到 `src/shared/prompts.ts`（放 shared 而非 main，因为 main 下的模块会连带引入 `electron`，纯 Node 测试跑不起来），**测试直接 import 同一份**。

同一毛病还出现在清理函数上：测试自己 `trim()` 就算了，没走应用的 `cleanCliOutput`，于是噪音行的问题在测试里一直失败、而实现里其实已被修好。改为 import 真实函数后一次通过。

**教训**：测试里**不要复制实现的逻辑或常量**。复制出来的那一份一定会漂移，而且漂移方向是「测试说失败、实现其实是对的」或更糟的「测试说通过、实现其实错了」。

### 3.2 间歇性失败：模型偶尔无视「不要调用工具」

实测：模型有时会尝试调用 `Bash`/`Read` 去探查项目。`--tools ""` 已禁用工具，**调用不会真的执行**，但 stdout 里会留下形如 `<｜｜DSML｜｜ invoke name="Bash">` 的畸形标记——不是计划正文，若当成功就会把垃圾写进文件。

处置：
1. 提示词里加「重要前提」段，明说没有可用工具、不要输出工具调用格式
2. 代码里加 `looksLikeToolCall()` 判定，**识别为失败而不是当成功**（宁可不产出，也不写垃圾进文档）
3. `generatePlan()` 包一层**自动重试一次**——这类失败是间歇性的，重跑通常就好；超时、找不到 CLI 等不重试
