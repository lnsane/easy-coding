# easyCode 编排功能 开发文档

> 版本：v0.5.0 ｜ 日期：2026-09-26
> 需求来源：`doc/markdwon的润色测试.md`（经润色整理后的版本）

## 1. 需求

在「编排」tab 中，配置角色（职责 / 职位 / 提示词），并在 markdown 编辑器上方新增「执行编排任务」按钮：点击后**以该 markdown 文档为需求说明，让 AI 在项目里把代码写出来**。

### 已确认的三个决策

| 决策点 | 选择 |
| --- | --- |
| 文档的角色 | **文档 = 需求说明**，AI 去改/新增项目代码 |
| 执行权限 | **允许写代码**（给读写工具，可执行命令） |
| 结果去向 | **追加「执行记录」一节到文档** |

> 需求文档里原本列了三条「待确认」，以上即为那三条的答复。

## 2. 数据模型

### 新表 `roles`

| 列 | 说明 |
| --- | --- |
| `id` | uuid |
| `name` | 角色名，如「前端工程师」 |
| `title` | 职位，如「高级前端」 |
| `duty` | 职责描述 |
| `prompt` | 该角色的提示词（作为 system prompt 追加给 Claude Code） |
| `builtin` | 是否为内置角色（内置不可删，可复制修改） |
| `created_at` / `updated_at` | 时间戳 |

### `creations` 新增一列

`role_id`（可空）：这份文档执行编排时默认用哪个角色。

### 新表 `runs`（执行记录）

| 列 | 说明 |
| --- | --- |
| `id` | uuid |
| `creation_id` | 关联创作 |
| `role_id` / `role_name` | 用到的角色（冗余存名字，角色被删也能追溯） |
| `branch` | 执行时所在分支 |
| `status` | `running` / `ok` / `failed` / `cancelled` |
| `started_at` / `ended_at` | 时间戳 |
| `log` | 完整执行日志（JSON 字符串） |
| `result_text` | AI 的最终输出文本 |

保留历史记录，便于回溯「这次改动是什么时候、由哪个角色做的」。

## 3. 执行流程

```
点击「执行编排任务」
  ├─ 1. 校验：文档非空、已关联项目、项目路径存在
  ├─ 2. 确认分支：切到该创作对应的分支（复用 ensureBranch，脏工作区拒绝）
  ├─ 3. 写回文档：把编辑器里的最新内容写入 doc/xxx.md
  │     （AI 要读的就是磁盘上的最新版本，不能是旧文件）
  ├─ 4. 记录 git 基线：git rev-parse HEAD，用于事后看改了什么
  ├─ 5. 执行：spawn claude -p，cwd=项目根，给读写工具
  ├─ 6. 实时推送日志到界面
  ├─ 7. 收集 git diff --stat 作为「实际改了什么」的证据
  ├─ 8. 追加「执行记录」一节到文档并落盘
  └─ 9. 写入 runs 表
```

### 与润色的关键区别

| | 润色 | 执行编排 |
| --- | --- | --- |
| 工具权限 | 仅 `Read` | **读写 + 可执行命令** |
| 是否改项目 | 否 | **是** |
| 结果去向 | 确认后替换文档 | 追加执行记录 |
| 是否需确认 | 必须逐处确认 | 直接执行，但**事前弹窗告知将要改文件** |

## 4. 安全设计（重点）

这是本项目**第一个会修改用户代码**的功能，必须有约束：

**1. 执行前明确告知。** 弹窗写明「将允许 AI 读取和修改 `项目路径` 下的文件，并可能执行命令」，用户确认后才开始。不能让用户误点。

**2. 依赖 git 分支兜底。** 执行前确保在创作对应的分支上（如 `v1.0`），改坏了可以 `git checkout` 回滚。执行记录里写入分支名与执行前的 HEAD，便于定位。

**3. 脏工作区拒绝。** 复用既有 `ensureBranch` 的约定 —— 有未提交改动就中止，避免把用户自己的改动和 AI 的改动混在一起分不清。

**4. 超时与可中止。** 长任务设置超时（默认 10 分钟），并支持用户主动中止（kill 子进程）。中止后仍记录已产生的日志。

**5. 不做自动提交。** AI 改完代码后**不自动 git commit**，由用户 review 后自己决定。这与既有约定一致。

**6. 提示词注入防护。** 文档正文是不可信输入，角色 prompt 与任务指令走 system prompt，文档只作为「需求文件」被读取。

## 5. 内置角色

首版内置五个常用角色，用户可复制后修改：

| 角色 | 职位 | 职责要点 |
| --- | --- | --- |
| 前端工程师 | 高级前端开发 | 按需求实现界面与交互，遵循现有组件风格 |
| 后端工程师 | 后端开发 | 按需求实现接口与数据逻辑 |
| 全栈工程师 | 全栈开发 | 前后端一并实现 |
| 需求分析师 | 产品经理 | 把需求整理成可执行的开发任务清单 |
| 代码审查员 | 技术负责人 | 审查现有实现是否符合需求，指出问题（**只读，不改代码**） |

`代码审查员` 特殊：其 prompt 里会要求只读不改，界面上也可标记该角色为只读角色（后续可扩展）。

## 6. 界面

### 编排 tab

```
┌─────────────────────────────────────────────┐
│ 角色  [+ 新建角色]                            │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐      │
│ │前端工程师 │ │后端工程师 │ │需求分析师 │ ...  │
│ └──────────┘ └──────────┘ └──────────┘      │
│                                             │
│ 选中：前端工程师 · 高级前端开发               │
│ 职责：按需求实现界面与交互…                   │
│ 提示词：[可编辑文本域]                        │
└─────────────────────────────────────────────┘
```

### markdown 编辑器

工具栏上方新增「⚡ 执行编排任务」按钮，右边显示当前绑定的角色（可下拉切换）。

### 执行面板

复用润色的 `PolishProgress` 模式（抽出通用的 `RunProgress`）：实时显示命令、工作目录、子进程输出、耗时，另加**中止按钮**。

执行结束后显示结果摘要：`改动 3 个文件，+120 −18`（来自 `git diff --stat`）。

## 7. 测试计划

| 层 | 内容 |
| --- | --- |
| L12 角色/运行数据层 | roles 与 runs 的 CRUD、内置角色初始化、run 状态流转 |
| L13 执行编排（真实仓库） | 用真实临时仓库 + 真实 claude CLI：验证能在项目里新建文件、git diff 能捕获改动、**中止能杀掉进程**、脏工作区拒绝执行 |
| L11 回归 | 润色文件模式不受影响（权限没被放宽） |

**必须专门测的安全项**：
- 执行前未确认时不得启动
- 中止后子进程确实被杀死（不留孤儿进程）
- 执行不会自动 commit

## 8. 实施顺序

1. 本文档
2. `shared/types.ts`：`Role` / `Run` 类型
3. `main/db.ts`：`roles`、`runs` 表 + CRUD + 内置角色初始化；`creations.role_id` 迁移
4. `main/orchestrate.ts`：执行编排（含中止、超时、git diff 收集）
5. IPC + preload
6. 组件：`RoleManager`（角色卡片 + 编辑）、`RunProgress`（由 PolishProgress 抽出通用化）、执行前确认弹窗
7. 编排 tab 接线 + 编辑器按钮
8. 测试 → 编译 → 实机验证
9. 版本文档

## 9. 明确不做

- 不做多角色流水线（一次只跑一个角色；多角色串联留待后续）
- 不做自动 git commit / push
- 不做执行结果的自动合并或冲突处理
- 不做「回滚到本次执行前」的一键撤销（用户可用 git 手动回滚，记录里有分支与 HEAD）
